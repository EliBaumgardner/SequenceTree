## How this file is maintained

- New findings are added, never silently replacing old ones. When a finding is fixed, it moves to "Fixed / re-checked" with the commit that fixed it.
- Every finding cites `file:line` at the commit named above. Line numbers drift: re-check a finding before acting on it.
- **Severity follows what a user can actually reach.** High: wrong output or data loss through normal use. Medium: behaviour a user can hit that is wrong, undocumented, or contradicts the code's own documentation. Low: needs a corrupt or hand-edited file, hand-built bytecode, a pathological script or an unrealistic load; or a cheap clean-up. A finding that needs a corrupt file is never above Low.
- **Settled** findings record the owner's decisions about deliberate behaviour. **Withdrawn** findings did not survive re-checking. Do not re-raise either unless the code they cite changes.
- A finding marked **Suspected** names the test or measurement that would settle it.

## Open — Medium

### A-H2 — Preview with a high count repeats rule selection for each alternative host on the audio thread
**Medium, Suspected: undecided until measured.** In Preview mode `begin()` replays `advanceAlternative` up to `visitCount - 1` times for every node that has an alternative (`Source/Core/Traversal/TraversalLogic.cpp:63-77`), and the count field allows up to 9,999 (`Source/Editor/Bars/BottomBar.cpp:22`). Each pass runs one rule selection. The cost was not measured.
The original fix (clamp the count to 64) is rejected: the seeded counts decide which alternative is sounding, and counts are compared against limits up to 9,999, so a clamp changes what preview plays.
Settle it: time one preview at count 9,999 with 1, 10 and 50 alternative hosts. Only if that is too slow for one block, look for a way to seed the counts that gives the same alternatives.

### G-H12 — A switch repeat returns before the group-loop diversion
**Medium; the owner decides which wins.** Confirmed from code on Day 3 (was "needs a test"). In `chooseChild`, `selectSwitchNode` runs first and returns early whenever a switch candidate exists with `switchCount < switchCountLimit` (`Source/Core/Traversal/ChildSelector.cpp:100-133`, the early return at `:107-112`; the repeat condition at `:249-270`). The group-loop diversion `encapsulationLoopTarget` is only consulted afterwards (`:124`, `:286-306`). So a group-exit child with a switch limit above 1 repeats via the switch and skips the group's sub-loop diversion for that step.
Fix: decide which wins and document it; if the group loop should win, check the diversion before the switch repeat. Test: a group whose exit child has a switch limit above 1 — the sub-loop should (or should not) run on the repeat step, per whichever precedence is chosen.

### G-M11 — A child with two parents can get `parentId` 0 when its first parent is built after it
**Medium.** Confirmed from code on Day 3 (was "needs a test"). `createRTNodes` sets `parentId` only if `getNodeParent`'s first-linked parent is already in `builtNodes` (`Source/Processor/AudioModel/RTGraphBuilder.cpp:462-478`), nodes are built once with no fix-up pass (`:412-414`), and `getNodeParent` returns the first-linked non-flag parent in link order (`Source/Processor/Document/Graph/GraphState.cpp:142-175`, `linkParent` appends at `:651-656`). `canConnect` allows a second parent, including a modulator→non-root child (`Source/Editor/Canvas/GraphDocument.cpp:159-168`). A shared child first reached via its second parent therefore keeps the default `parentId` 0 (`Source/Core/Model/RTData.h:126`), which terminates `ModulatorWalk::isDescendantOf` (`Source/Core/Traversal/ModulatorWalk.cpp:270-296`) and makes the script `parent` field read -1 (`Source/Core/Traversal/ScriptRun.cpp:460-464`).
Fix: after the build, set `parentId` from `getNodeParent` for any node whose parent is now built, or build in an order that guarantees the first-linked parent first. Test: a child shared between a node and a modulator, checking `parentId` and modulator stepping.

### G-H8 — A grouped node can be a span's first click, and is then stolen into the new group
**Medium; the `insertNodeAfter` half stays not-a-defect.** Confirmed from code on Day 3 (was "needs a test"). `selectSpanNode` checks only node type (`Source/Editor/Encapsulation/EncapsulationGestures.cpp:20-62`): a first click on a grouped node sets it as the span anchor unconditionally. `nodeIdsBetween` filters grouped *neighbours* and *descendants* but pushes the anchor unconditionally into the span (`Source/Processor/Document/Graph/GraphState.cpp:433-500`). `EncapsulationOps::create` then overwrites that node's `EncapsulatorId` without removing it from the old group's `EncapsulatedIds` list (`Source/Processor/Document/Graph/EncapsulationOps.cpp:10-38`). Follow-on damage: dissolving the old group resets the stolen node's property (`:60-68`), orphaning it from the new group while the new group's list still names it — and the two sides disagree visibly, since the canvas reads the list (`Source/Editor/Encapsulation/Encapsulator.cpp:30`) while copy/group logic reads the property (`Source/Processor/Document/Graph/Clipboard.cpp:429-463`), so the node shows in both groups.
Fix: refuse a grouped anchor in `selectSpanNode`, or make `create` detach each member from its old group first. The `insertNodeAfter` half cannot happen: its only caller passes a freshly created child (`Source/Editor/Canvas/NodeController.cpp:19-21`), and it refuses duplicates in the same group (`Source/Processor/Document/Graph/EncapsulationOps.cpp:108-111`). Note: `insertNodeAfter` also doesn't check cross-group membership — unreachable today, defence-in-depth only.

### Script language
- **S-M2** — The ban on `advance` / `playNote` inside `advance` checks only the function named `advance` (`Source/Core/Script/ScriptEmitter.cpp:940-943`, `:976`). A helper bypasses it, but the nested call then returns `none` or does nothing, so this is a missing diagnostic, not a safety problem. Re-checked on Day 3 and confirmed by probe: a helper calling `advance` from `advance` compiles; at run time `advance` runs with `host == nullptr` (`Source/Core/Traversal/TraversalLogic.cpp:329,402,569`), so the nested call returns `none` (`Source/Core/Traversal/ScriptRun.cpp:356-360`) and a nested `playNote` does nothing (`:375-392`).
- **S-M7** — `-2147483648` cannot be written, because the lexer rejects `2147483648` (`Source/Core/Script/ScriptLexer.cpp:96-134`) before `parseUnary` folds the minus (`Source/Core/Script/ScriptParser.cpp:815-821`). Re-checked on Day 3 by probe: `-2147483648` → "number is too large"; `-2147483647` compiles.
- **S-L3** — There is no cap on the size of a compiled script; only execution is capped (`Emitter::emit` appends with no limit, `Source/Core/Script/ScriptEmitter.cpp:780-793`). Re-checked on Day 3 by probe: 20,000 assignments compile to 40,004 instructions; 500 functions compile. Function count and constants are also uncapped. Only execution is capped (step budget 8,192).
- **S-L9** — The VM reads 0 for an out-of-range field or context operand instead of faulting (`Source/Core/Traversal/ScriptRun.cpp:468` via `PushNodeField` at `:318`; `Source/Core/Traversal/ScriptRun.cpp:510` via `PushContext` at `:296`). Only hand-built bytecode can reach it; the compiler never emits one. Corrected on Day 3: the convert half does *not* read 0 — `convert` returns the value unchanged for an unknown target (`Source/Core/Traversal/ScriptRun.cpp:619`). Same family: `calculate`'s unknown-number path and `execute`'s unknown-opcode fallthrough to the binary path (`realArithmetic` default 0.0). (B-H5 merged here.)
- **S-L11** — New on Day 3. A field assignment in a function with 32 live locals is falsely rejected. `emitAssignField` allocates a scratch slot with `allocateSlot()` (`Source/Core/Script/ScriptEmitter.cpp:357`), which raises `highWaterSlot` (`:806-812`). The slot is released afterwards (`--emitting.nextSlot;`, `:407`) but the high-water mark stays raised, and `emitFunction` rejects `highWaterSlot > RTScript::maxLocals` (`:156-158`). Verified by probe: 32 locals + `current.count = 1;` → rejected with "too many variables for the traversal stack", while 31 locals + the same line compiles, and 32 locals alone compiles. Both `=` and `+=` are affected (the slot is allocated for every field assignment). The guide says a function can hold 32 locals, so a legal program is refused — loud compile error, needs a script at the exact limit, hence Low. Fix: don't let the transient scratch slot raise `highWaterSlot` (save/restore it around the allocation in `emitAssignField`), or reserve one scratch slot outside the 32. Test: 32 locals + `current.count = 1;` compiles; 33 locals still rejected.
- **S-L12** — New on Day 3. S-L2 residual: an unclosed *nested* block still yields one identical diagnostic per open block. The `0f77038` fix only suppresses the class-level duplicate. Probe: `void main() { if 1 { int a = 1;` at end of file → 2 diagnostics, both `expected '}'`, one from the `if`-body `parseBlock` and one from the function-body `parseBlock`, both at end of file (`Source/Core/Script/ScriptParser.cpp:429-441`). Nuance: two blocks genuinely are unclosed, so two diagnostics is defensible counting — the noise is that they are identical and location-identical, so the user cannot tell which block each refers to. Fix (optional): when a `parseBlock` fails with `unclosedBlock`, have the enclosing `parseBlock` propagate the failure instead of adding its own `expected '}'`. Or leave as-is; it is diagnostic noise on malformed scripts only.
